# SmartLoo – Data Model & Security Requirements

**Owner:** Fırat (DB & Security)
**Scope:** Toilet, User and Review entity models; authentication and authorization with JWT.
**Status:** Integrated review candidate. See REQUIREMENTS.MD for the integration decisions and canonical API contract.

> Note on IDs: `REQ-DB-xx` / `REQ-SEC-xx` are used for requirements and `TS-DB-xx` / `TS-SEC-xx` for test specifications, so they do not collide with the functional tests `TC-01..TC-10`. The PM may renumber them during the final merge.

## 1. Data Model Requirements

### REQ-DB-01 – Toilet entity (Must)
The system shall store each public toilet with the following fields:

| Field | Type | Rules |
|---|---|---|
| `id` | UUID | Primary key, generated by the system |
| `ibb_source_id` | string, nullable | Unique when present; ID from İBB Open Data |
| `name` | string (max 150) | Required |
| `latitude` | decimal | Required, between -90 and 90 |
| `longitude` | decimal | Required, between -180 and 180 |
| `district` | string | Required (e.g. "Kadıköy") |
| `address` | string, nullable | |
| `has_disabled_access` | boolean | Nullable: unknown is not treated as false; used by the accessibility filter |
| `has_baby_changing` | boolean | Nullable; unknown when absent |
| `is_free` | boolean | Nullable; unknown when absent |
| `opening_hours` | string, nullable | |
| `status` | enum | `ACTIVE`, `CLOSED`, `MAINTENANCE`; default `ACTIVE` |
| `average_cleanliness` | decimal (1–5), nullable | Derived from reviews (see REQ-DB-05) |
| `review_count` | integer | Derived, default 0 |
| `created_at`, `updated_at` | timestamp | Set by the system |

### REQ-DB-02 – User entity (Must)

| Field | Type | Rules |
|---|---|---|
| `id` | UUID | Primary key |
| `email` | string | Required, valid format, unique (case-insensitive) |
| `password_hash` | string | Required; plaintext passwords are never stored (see REQ-SEC-01) |
| `display_name` | string (3–30) | Required |
| `role` | enum | `USER`, `ADMIN`; default `USER` |
| `is_active` | boolean | Nullable; unknown when absent |
| `created_at` | timestamp | Set by the system |

### REQ-DB-03 – Review entity (Must)

| Field | Type | Rules |
|---|---|---|
| `id` | UUID | Primary key |
| `toilet_id` | UUID | Foreign key → Toilet, required |
| `user_id` | UUID, nullable | Foreign key → User (null after the author's account is deleted, see REQ-DB-04) |
| `cleanliness_score` | integer | Required, 1–5 |
| `comment` | string (max 1000) | Optional |
| `created_at`, `updated_at` | timestamp | Set by the system |

A user may write **at most one review per toilet** (unique constraint on `toilet_id + user_id`).

### REQ-DB-04 – Referential integrity and data deletion (Must)
- A review cannot be created for a toilet or user that does not exist.
- Toilets are never hard-deleted while they have reviews; they are marked `CLOSED` instead.
- When a user deletes their account, their personal data (email, display name, password hash) is removed and their reviews remain with `user_id = null`, shown as "Anonymous" (privacy requirement; this alone does not establish legal compliance).

### REQ-DB-05 – Rating aggregation (Must)
When a review is created, updated or deleted, `average_cleanliness` and `review_count` of the related toilet shall be recalculated before success is acknowledged to the caller; cross-store coordination is a design decision.

### REQ-DB-06 – Idempotent İBB import (Should)
Importing İBB Open Data shall insert new toilets and update existing ones matched by `ibb_source_id`, without creating duplicates. (Interface with Emir Miraç's API integration task.)

## 2. Security Requirements

### REQ-SEC-01 – Registration and password storage (Must)
- `POST /api/v1/auth/register` with `email`, `password`, `display_name`.
- Password policy: at least 8 characters, containing at least one letter and one digit.
- Passwords are hashed with bcrypt (cost ≥ 10) or Argon2 before storage.
- Duplicate email returns **409 Conflict**; invalid input returns **422 Unprocessable Entity**.

### REQ-SEC-02 – Login and JWT issuance (Must)
- `POST /api/v1/auth/login` with `email` and `password`.
- On success the system returns **200 OK** with a signed JWT access token.
- Token claims: `sub` (user id), `role`, `iat`, `exp`. Access token lifetime: 60 minutes.
- On wrong email or password the system returns **401 Unauthorized** with the same generic message for both cases (no user enumeration).

### REQ-SEC-03 – Protected endpoints (Must)
Endpoints that change data (writing/editing/deleting reviews, admin operations) require an `Authorization: Bearer <token>` header. A missing, expired, malformed or tampered token returns **401 Unauthorized**. Read-only endpoints (map search, toilet details, reading reviews) are public.

### REQ-SEC-04 – Role-based authorization (Must)
Admin endpoints (`/api/v1/admin/**`, e.g. dashboard metrics and CSV/JSON export) are accessible only to users with role `ADMIN`. A valid token with role `USER` returns **403 Forbidden**.

### REQ-SEC-05 – Review ownership (Must)
A user can edit or delete only their own reviews. Attempting to modify another user's review returns **403 Forbidden**. Admins may delete any review (moderation).

### REQ-SEC-06 – Sensitive data handling (Must)
- `password_hash` is never included in any API response.
- The JWT signing secret is read from an environment variable and is never committed to the repository.
- All traffic in production is served over HTTPS.

### REQ-SEC-07 – Brute-force protection (Should)
After 5 failed login attempts for the same email within 15 minutes, further attempts return **429 Too Many Requests** until the window expires.

**Out of scope for Sprint 1:** refresh tokens, OAuth/social login, password reset by email.

## 3. User Stories

**US-DB-01** – As a **map user**, I want toilets to have accurate location and accessibility information, so that I can find a toilet that suits my needs. *(REQ-DB-01)*

**US-DB-02** – As a **registered user**, I want to rate and comment on a toilet once, so that other users can see reliable feedback. *(REQ-DB-03, REQ-DB-05)*

**US-DB-03** – As a **registered user**, I want my personal data removed when I delete my account, so that my privacy is protected. *(REQ-DB-04)*

**US-SEC-01** – As a **visitor**, I want to create an account with a secure password, so that I can write reviews. *(REQ-SEC-01)*

**US-SEC-02** – As a **registered user**, I want to log in and stay authenticated, so that I can perform actions that require an account. *(REQ-SEC-02, REQ-SEC-03)*

**US-SEC-03** – As an **admin**, I want the admin panel to be accessible only to admins, so that metrics and exports are protected. *(REQ-SEC-04)*

**US-SEC-04** – As a **registered user**, I want only me to be able to change my reviews, so that nobody can impersonate me. *(REQ-SEC-05)*

## 4. BDD Scenarios

User stories and key BDD scenarios are defined in this document. Runnable contract cases are in [requirements_cases.json](../../tests/requirements_cases.json).

```gherkin
Scenario: Successful login returns a JWT
  Given a registered user with email "ali@example.com" and password "Guvenli123"
  When the user logs in with email "ali@example.com" and password "Guvenli123"
  Then the response status is 200
  And the response contains an access token
  And the token contains the claims "sub", "role", "iat" and "exp"

Scenario: Regular user cannot access the admin panel
  Given a logged-in user with role "USER"
  When the user requests GET /api/v1/admin/metrics/summary
  Then the response status is 403

Scenario: A user cannot review the same toilet twice
  Given a logged-in user who has already reviewed toilet "Kadıköy İskele WC"
  When the user submits another review for "Kadıköy İskele WC"
  Then the response status is 409
  And the toilet's review_count does not change
```
